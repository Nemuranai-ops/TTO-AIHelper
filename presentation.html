The Test Analyst
Agent System

An agent system that decides what needs testing, designs the cases, and generates the automation — from the requirements, designs and code you already have.

Greenfield · no existing suite 8 units · 35 tools 951 tests passing

The problem

No test suite, no framework,
and roughly six thousand cases to write.

The inputs are scattered across systems that don't talk to each other: Jira stories, Confluence pages, Figma screens, Bitbucket repositories, Swagger files. A person can hold one feature's worth of that in their head. Nobody can hold a hundred and fifty.

So the first baseline gets built by whoever has capacity, in whatever order seems reasonable, and six months later nobody can answer the only question that matters: is this coverage actually complete, and how would we know?

What "done" has to mean

  • Every case traces to a Jira key
  • Every figure traces to a query
  • Every decision traces to a human who approved it

The constraint that shaped everything

There are no LLM API keys.

The agent must operate entirely through the models and capabilities the corporate GitHub Copilot environment exposes.

That single line rules out the obvious architecture. TAAS cannot be a service that calls a model in a loop, because there is nothing to call.

So it is two things instead

A VS Code Copilot workspace — chat modes, instructions, prompt files, MCP registration — paired with a deterministic local toolchain that owns every fact which must stay true across thousands of records.

The constraint turned out to be the best thing about the design. A model that can't be trusted to count is never asked to.

The organising principle

The model reasons about meaning.
Deterministic code guarantees the rest.

The model decides

  • What a story actually asks for
  • Which behaviours are worth testing
  • What the steps of a case should be
  • Whether two screens mean the same thing
  • Which locator identifies an element

All judgement. All things a person would do, and would occasionally get wrong.

The toolchain guarantees

  • Every case has ordered steps and expected results
  • Every case resolves to an ingested Jira key
  • No duplicate enters the corpus
  • Identifiers are allocated once and never reissued
  • Every figure in every report is a query result

Not "the instructions say so". Schema constraints, database triggers, and import contracts that fail the build.

Steps 03–05 are the three read-only servers, and they are where the corpus gets its evidence: a story, an endpoint the story forgot, and a locator that provably matches something. Two of the three ship inside this repository — clone it, and there is nothing left to configure. tto-bitbucket goes further still: it reads git clones already on disk and never reaches Bitbucket’s network at all.

Had the agent invented a Jira key at step 07, the batch would have been refused at the database. It can only cite keys that were actually ingested.

Architecture

Hexagonal, with the domain at the centre
and nothing pointing outward.

Agent layer 7 Copilot chat modes · instructions · prompt files. No file-write tools — durable state can only go through the toolchain.
depends on
MCP boundary 35 tools — 17 read, 18 write. Pydantic validation, typed result codes, remediation text on every rejection.
Services S1–S9. Own transaction boundaries and orchestration. Never call a concrete adapter.
Ports Protocols only. The source ports declare no write method — read-only against Jira and Bitbucket is a missing capability, not a rule.
Domain D1–D8 + 5 pure modules. Similarity, identity, traceability, coverage, classification, impact, validation, privacy. Imports nothing but stdlib.
Adapters SQLite, MCP clients, Jinja2 emitter, subprocess runner. Swappable without the domain noticing.

5 import contracts enforce this at build time. One of them confines subprocess to a single module — and it was verified by deliberately breaking it.

Gate

The coverage gate is the binding one. Approval attaches to a content hash of the model — rebuild it unchanged and the approval survives; change one requirement and it is invalidated, and the system says so before anything downstream runs.

Nothing regenerates itself. A delta run re-enters the pipeline at stage 03, through the same gates the baseline passed.

The agent writes the case. The toolchain checks it.

// submitted by the agent — note: no identifier field
{

  title:  "Reject a quantity of zero",
  test_type: "boundary",
  steps: [
    { ordinal: 1, action: "Open the basket",
      expected: "The basket page is shown" },
    { ordinal: 2, action: "Set quantity to 0",
      expected: "An out-of-range message is shown" } ],
  test_data: [
    { field: "quantity", value: "0",
      equivalence_class: "boundary-low" } ],
  trace_links: [ { type: "direct-story",
                    jira_key: "PAY-12" } ]
}

Eleven checks, in order

ACoverage gate open and unchanged
ABatch within the 200 cap
BIdentifier not caller-supplied
BSteps present, each with an expected result
BTest data carries an equivalence class
BNo real personal data in any value
CJira key resolves to an ingested artefact
DNot a duplicate of the corpus or the batch
EAutomatability classified
FIdentifier allocated — only now

All-or-nothing. One bad case rejects the batch, every fault is reported together, and no identifier is consumed — so the corrected batch starts at the same number.

Pure @playwright/test. No custom runner, no framework to learn. Page objects, a shared auth fixture, HTML and JUnit reporters, and a pinned version.

What the templates refuse to emit

  • Fixed waits. No template fragment produces one — every step yields an action and an assertion
  • XPath. Absent from the locator ladder, not last on it
  • Literal credentials or environment URLs. The emission is refused entirely

A red test in Jenkins carries its own provenance. You never have to query the corpus to learn which story a failure belongs to.

The design idea that repeats

Rules people can forget
became capabilities that don't exist.

The ruleHow it cannot be violated
Read-only against Jira and BitbucketThe source protocols declare no write method
The agent never picks the next unit of workThe run-state service has no next_unit()
The system never pushes or configures JenkinsThe handover service has no push
A delta run never regenerates behind a gateThe delta service cannot create a case
A case must have steps and a real Jira keyDatabase triggers, not validation alone
The agent cannot supply its own identifierThe payload type has no id field
No unit reimplements a domain algorithmImport contracts fail the build

Seven places where the honest answer to "what stops this?" is nothing can do it — rather than we wrote it down.

Deliverables

What you actually get.

The corpus

SQLite as the system of record. Every case with steps, synthetic data, equivalence classes, tags and traceability links.

Plus Markdown and YAML views per feature, for review.

The automation

A complete, runnable Playwright project — config, lockfile, page objects, fixtures, specs, .env.example and a README.

Structurally verified before it's declared ready.

The evidence

Coverage, gap, automation and delta reports. A bidirectional traceability matrix in Markdown and CSV.

Every figure carries the query it came from.

Your edits survive. Every generated file records a hash when it's written. Edit a spec or tune playwright.config.ts, and the next run reports it as hand-edited and leaves it alone.

The generated suite is a starting point, not something you can't touch. That distinction is enforced, not promised.

Boundaries

What it deliberately doesn't do.

  • It doesn't push to Bitbucket. You push, and you configure the Jenkins job
  • It doesn't run the tests. Execution stays in your existing pipeline
  • It doesn't write to Jira or Confluence. Read-only, structurally
  • It doesn't delete a test case. Ever — retirement marks and retains
  • It doesn't choose what to work on next. You do

And one limit worth stating plainly

The suite proves the toolchain is correct. It cannot prove the agent reasons well — which is exactly what the human gate at every stage is for.

The system's claim is narrower than "it writes your tests", and checkable: every case traces to a story, every figure to a query, every decision to a person.
