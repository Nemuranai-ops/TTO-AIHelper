## A constraint that needs a decision before anything is designed

Three acceptance criteria require a **Node toolchain**:

| Criterion | Needs |
|---|---|
| US-HND-01 AC1 — `package-lock.json` is present | `npm install` |
| US-HND-02 AC2 — TypeScript compilation succeeds | `tsc` |
| US-HND-02 AC3 — `playwright test --list` enumerates | `npx playwright` |

TAAS is a Python toolchain. U5 explicitly declined to make its own test suite depend on
Node, and that decision stands — but **U6 cannot satisfy its acceptance criteria without
one**, because a lockfile cannot be synthesised and a compiler cannot be simulated.

This is not a problem with the requirement. It is a real property of the deliverable:
the operator is handed a Node project, so a Node toolchain exists somewhere in their
workflow. The question is what U6 does when it is not on the machine running TAAS —
and Question 1 settles it before anything else is designed.

**Four questions.**

## Question 1 — Business Rules: verification when Node is absent

A) **Verification has two tiers. Structural checks always run in Python — every
referenced page object, fixture and data file exists, every manifest entry has a test
and every test has an entry. Toolchain checks (`npm ci`, `tsc --noEmit`,
`playwright test --list`) run when Node is present and are reported as `skipped` with
the reason when it is not. Handover is declared ready only when the structural tier
passes, and the report states plainly which tier ran.**
**(Recommended — the structural tier catches the failure US-HND-02 AC4 names, which is
the common one; and a report saying "compilation not verified: Node not found" is
honest, where silently passing would be a false assurance the engineer acts on)**

B) **Require Node.** Refuse to run without it. Faithful to the criteria, and it makes
the whole unit unusable on a machine that has Python and not Node — including, quite
possibly, the operator's.

C) **Structural checks only.** Never invoke Node. Simple, and it declines to catch the
compilation failure the engineer would otherwise find in Jenkins, which is the reason
US-HND-02 exists.

X) Other (please describe after [Answer]: tag below)

[Answer]: A — two tiers; toolchain checks reported as `skipped` when Node is absent (accepted via "Accept all recommendations")

## Question 2 — Business Rules: how the lockfile is produced

`package-lock.json` cannot be written by hand — it records a resolved dependency graph.

A) **Generated by `npm install --package-lock-only` when Node is present; when it is
not, the file is absent and the handover report says so, with the one command the
operator must run before pushing.** **(Recommended — `--package-lock-only` resolves the
graph without downloading packages, so it is fast and needs no network beyond the
registry metadata; and naming the exact command turns a missing file into a two-second
fix rather than a puzzle)**

B) **Always require it**, failing handover when Node is absent. Consistent with
Question 1 option B and inherits its problem.

C) **Commit no lockfile.** The engineer runs `npm install` and commits the result.
Simpler, and it means the first CI run resolves versions independently of what was
verified — which is the drift FR-HND-02 exists to prevent.

X) Other (please describe after [Answer]: tag below)

[Answer]: A — `npm install --package-lock-only` when Node is present; reported with the command when not (accepted via "Accept all recommendations")

## Question 3 — Data Model: assemble in place, or into a handover directory

U5 already writes a complete project to `generated/automation`.

A) **Verify in place and add only what is missing** — `.gitignore`, the lockfile, the
manifest. `generated/automation` **is** the handover directory. **(Recommended — a copy
would create two projects that can disagree, and the one the engineer pushes would be
the one nothing verified; U5's hand-edit protection already covers this directory)**

B) **Copy into `handover/`**, leaving `generated/` as working output. A clean
separation, and a copied hand-edit is no longer tracked by the hash that protects it.

C) **Assemble into a timestamped directory** per handover. Full history, and it
multiplies the corpus's largest artefact on every run for a history git already keeps.

X) Other (please describe after [Answer]: tag below)

[Answer]: A — verify in place; `generated/automation` is the handover directory (accepted via "Accept all recommendations")

## Question 4 — Business Rules: what the manifest reconciles against

US-HND-03 AC3 requires a mismatch in either direction to block handover.

A) **Three-way: the `automated_test` table, the spec files on disk, and the manifest.
Any disagreement between the three is named and blocks readiness.**
**(Recommended — two-way against the database alone would miss a spec file deleted by
hand, and against disk alone would miss a test the database believes exists; the
three-way check is the only one that catches both)**

B) **Two-way, database against manifest.** Cheaper, and it trusts that disk matches the
database — which stops being true the moment anyone edits the project, which the design
explicitly permits.

C) **Two-way, disk against manifest.** Verifies what is being handed over, and cannot
tell whether it matches what the corpus says was generated.

X) Other (please describe after [Answer]: tag below)

[Answer]: A — three-way: `automated_test`, disk, and the manifest (accepted via "Accept all recommendations")
