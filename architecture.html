Architecture sheet  ·  TTO Test Analyst Agent System

Where every fact comes from tto-testgen — the deterministic toolchain behind TAAS

TAAS is two halves. The agent layer — Copilot instructions, chat modes and prompt files — reasons about meaning. This repository is the other half: the code that owns every fact which must stay true across thousands of test cases. These plates show the seam between them, and the four different doors that information comes in through.

Plate 1

Process topology

tto-testgen is both an MCP server (to Copilot) and an MCP client (to two other servers, for bulk reads — fetching hundreds of Jira issues through the model's own context would be slow and expensive). Every connection below is a real, separate stdio channel; nothing here shares a process or a socket.

  • Wire — a structural stdio connection held open for the session
  • Dashed — an MCP session opened for one call, then closed
  • Rust — leaves this machine; a credential is involved
  • Green — local disk only, never the network
  • Violet — the probabilistic half: the model and what it drives

Four things to read off the plate

  • Nothing here holds a credential except tt-atlassian-mcp's own .env, which TAAS never reads. tt-bitbucket-mcp never contacts a network at all — it reads git clones already on disk.
  • Every arrow into tto-testgen from Atlassian or Bitbucket is a fresh session, opened for one call and closed immediately — not a connection held open for the life of the process. A call that cites a direct Jira link never opens one at all.
  • API contracts are discovered, not fetched. The spec's location comes back from the repository scan; its content does not. Plate 2 shows exactly where that line falls.
  • Design information arrives as an exported folder, not a Figma API call. No MCP server sits between tto-testgen and the images, and the image bytes never leave the folder — only a hash does. Plate 3.

A single request walks this graph more than once. Asking Copilot to generate test cases for a feature typically ingests through both vendored servers first (their sessions open and close), builds the requirement and coverage model against SQLite, and only then generates — each step a separate, auditable tool call, never one opaque action.

Source register

Eight rules, one file

Every source is declared as a plain link in resources.md — nothing is labelled by hand. Classification applies the rules below in order, first match wins; the order is a design decision, not an accident of authorship. Plate 2

Where API contracts come from

You will rarely declare a Swagger or OpenAPI file yourself. The system finds specs on its own while reading a Bitbucket repository — and stops at the file's path, deliberately, because the vendored server exposes no tool that returns a file's raw content.

  • The five filenames matched are swagger.json, openapi.json, swagger.yaml, openapi.yaml and openapi.yml, tested against the repository's git ls-files listing — so an untracked spec is invisible, by the same rule that makes the scan reproducible.
  • Paths surface as spec_files_found on the api_model_derive result, prefixed with the repository slug (checkout-service:docs/openapi.yaml), and in the human-readable output as "the best source for expected results the test cases are missing."
  • Why the derivation stops there. tt-bitbucket-mcp has no tool that returns a file's raw bytes — bitbucket_file's structured payload carries no content field, and its text output is a line-numbered human-readable snippet, not parseable source. A spec's location can be surfaced honestly; its shapes cannot be, without a capability the server does not currently expose.
  • A spec declared standalone (rule 7) has no fetcher at all. This system has no generic HTTP fetcher, so rather than inventing one, the type resolves to the existing "no adapter for this type" error. The classification still happens, so the entry is reported rather than silently dropped.

Consequence for the reader

When a plate or a report cites an endpoint's shape — request body, status codes, auth — that came from the code scan or from a human, never from a spec file the system parsed. Open the reported path and compare it yourself. Endpoint status_codes stays empty and auth_requirement stays UNKNOWN when the scan found no evidence either way; that is the required behaviour, not a gap in the data.

Plate 3

Where design information comes from

There is no Figma integration and no Figma token. Design information enters as a folder of exported screenshots that someone drops into the repository, and a filename convention does the work an API would otherwise do. A directory path in resources.md is the only classification rule that touches the filesystem.

Filename convention · src/tto_testgen/adapters/sources/design_assets.py
FilenameSegmentsResult
checkout__cart.png2feature checkout, screen cart, state defaults to default
checkout__cart__empty.png3feature, screen and state all taken from the name
cart.png · a__b__c__d.png1 or 4+Reported as unassociated, by name — never guessed at, never dropped
  • Accepted image types are .png, .jpg, .jpeg and .webp. Everything is slugified — lowercased, non-alphanumerics collapsed to hyphens — so Checkout Cart and checkout-cart resolve to the same screen.
  • The sidecar overrides one field at a time. A manifest entry can correct just the route or just the jira_key without restating the rest — and a restatement is a chance to introduce an error. Each asset records an origin map saying which value came from the filename and which from the manifest, so a field-by-field override stays auditable.
  • The sidecar is untrusted input. It is parsed with yaml.safe_load, not yaml.load, because a shared design folder is exactly the kind of place a file arrives from without review.
  • Unassociated files are surfaced, not swallowed. The ingestion report names the first five and counts the rest, on the same guidance channel every other resource's notices use.

Operationally

Export from Figma at whatever fidelity you like, name the files feature__screen__state.png, drop them in designs/<feature>/, add that directory to resources.md, and say "ingest the resources for checkout." Add a screens.manifest.yaml beside them only when a filename cannot carry something — a route, or the Jira key a screen belongs to.

Plate 4

Seven stages, one gate at a time

Copilot Chat works in one of seven modes, one per stage, selected from the chat mode dropdown. Each mode names the tools visible in it, works on one feature at a time, and stops after one stage — it will not choose the next one for you. A stage cannot begin until the previous one is complete, approved, and unchanged since approval; unit_begin enforces that, not convention.

Interrupted work loses nothing, because it is transactional: /resume-run reports what is interrupted, what is complete and approved, and the corpus totals — and deliberately recommends nothing. delta_detect runs at any stage and answers the standing question of whether the ground moved since the last completed run.

Plate 5

Layering, and what holds it

Dependencies point inward. The contract that matters most is that domain/ imports nothing outside the standard library and itself — that is the precondition for the property suite. The moment a domain module imports an adapter, the properties need a database and stop being cheap enough to run on every commit.

Enforcement

What the toolchain refuses

These are refusals, not warnings. Each exists because the alternative is a corpus nobody can trust — and a rule the model is merely asked to follow erodes over 6,000 cases and many sessions, where a rule the storage layer enforces does not.

Domain validators, service gates and database constraints

A completed unit is not re-run without an explicit instructionunit_begin

The two most important rules are enforced twice, in the domain and in the schema. The validator produces an error the agent can act on; the constraint makes the rule unbreakable even if a future code path bypasses the validator. Neither alone is enough: a constraint gives an unhelpful error, and a validator can be forgotten.

Recovery, in two mechanisms because they cover different failures

  • Backups (.taas/backups/, newest 10 retained, one taken automatically before any migration) restore byte-identically, but are only readable by a compatible schema version.
  • Exports (generated/exports/, JSON Lines per table) survive a database the current code can no longer open.
  • Every forward migration ships a tested reverse, so rolling back to a release tag and reverting the schema is a supported path rather than an emergency.

Boundaries

Not in scope

Test execution and Jenkins orchestration. This system generates tests and packages them; the pipeline runs them. It never pushes to a repository and never writes Jenkins configuration.

Nor does it fetch a spec over HTTP, call the Figma API, or hold a Bitbucket credential — three capabilities it could plausibly be assumed to have, and deliberately does not. Plates 2 and 3 exist largely to make that legible before someone designs around the assumption.
